# Скиллы

Источник: GDD «Скиллы» (версия 2026-10-01). Механика общая для персонажей, мобов, саммонов и снаряжения; все скиллы лежат в листе `Skills` и привязываются к носителю по id.

## Конфиг

| Колонка | Что внутри |
| --- | --- |
| `id` | id скилла, он же ссылка из `skill_ids` / `skill_id` носителя |
| `triggers` | условия активации |
| `actions` | целевые действия |

Формат обеих колонок одинаковый:

```
<компонент>:[<параметр>:{аргументы}, <параметр>:{аргументы}]; <компонент>:[...]
```

Разделители по общему правилу конфигов (подтверждено геймдизайном 2026-10-02): **первый порядок `;`, второй `,`, третий `:`**. Применительно к скиллам:

- компоненты разделяются `;`;
- параметры внутри `[...]` — `,`;
- аргументы внутри `{...}` — `:`;
- аргументы внутри `{...}` перечисляются по уровням прокачки скилла: первый аргумент — базовый уровень, дальше по одному на каждую прокачку;
- парсер боя принимает и `,` вместо `:`, но публикация конфигов на такую строку выдаёт предупреждение: запятая внутри `{}` однажды прочитается как два аргумента там, где имелась в виду дробь;
- если уровень скилла выше, чем число аргументов, берётся последний аргумент;
- переводы строк и пробелы игнорируются.

Устаревшие колонки `type`, `proc_order`, `parameters` помечены необязательными: пока строка не переведена на `triggers` / `actions`, она собирается старой фабрикой скиллов. Как только лист переведён целиком, старый путь можно удалить.

## Условия активации

Несколько условий = И: скилл активируется только если выполнены все.

| Условие | Параметры | Поведение |
| --- | --- | --- |
| `energy_needed` | `energy` | накопленная ЭНЕРГИЯ носителя не меньше значения; активируется в фазе энергоскилла (после обычных атак), при активации энергия обнуляется |
| `ally_health_lower` | `health`, `is_instant_activation` | у союзного main-юнита текущее ХП / МАКС.ХП не больше порога; повторно разрешается только после того, как ХП снова поднялось выше порога; при `is_instant_activation = 1` может срабатывать вне очереди |
| `on_cooldown` | `cooldown`, `is_start_availiable` | с начала боя или с последней активации прошло не меньше N ходов; `is_start_availiable = 1` разрешает активацию на первом ходу |

## Целевые действия

Действия выполняются в порядке возрастания `timing`; между ними сервер ставит `Wait` на разницу таймингов. От действий скилла нельзя уклониться, крита у них нет.

| Действие | Параметры | Поведение |
| --- | --- | --- |
| `damage` | `damage`, `target`, `is_spell_amp`, `timing` | урон = итоговый ДМГ носителя × `damage`, при `is_spell_amp = 1` ещё × СПЕЛЛ_МН. **ЗАЩИТА цели не применяется.** У скилла саммона берётся ДМГ самого саммона |
| `set_status` | `status_id`, `target`, `timing` | статус из `Statuses` на цель; дальше работает общая логика статусов, включая `status_target` |
| `set_bonus` | `bonus_id`, `target`, `timing` | бонус из `Bonuses` на цель, дальше общая логика бонусов и `work_modes` |

Цель (`target`): `0` — союзник (сам носитель), `1` — враг в первом слоте с откатом на второй, `2` — враг во втором слоте с откатом на первый, `3` — все живые враги.

## Уровень скилла

Для персонажа уровень берётся из `promote_to_skill_levels` в листе `Characters`: это массив уровней промоута, индекс значения = индекс набора значений внутри скилла. При `0;1;3;5` и промоуте 2 скилл всё ещё использует вторые значения (индекс 1). У мобов, саммонов и снаряжения уровень пока 0 — прокачка скиллов саммонов ждёт таблицу стоимостей от геймдизайна.

## Внеочередная активация

После каждого удара атакующей стороны (обычная атака, комбо, контратака) сервер проверяет скиллы обеих сторон, у которых стоит `is_instant_activation`, и если условие выполнилось — проигрывает скилл сразу, не дожидаясь фазы скиллов. Порядок бросков случайности при этом не меняется: проверка не тратит RNG.

## Как добавить новое условие или действие

1. Добавить значение в `SkillTriggerType` или `SkillActionType`.
2. Реализовать `ISkillTriggerEvaluator` или `ISkillActionExecutor` (имя компонента возвращает `TypeKey`).
3. Зарегистрировать в `BattleComposition.CreateSkillTriggerEvaluators` / `CreateSkillActionExecutors`.
4. Дописать строку в таблицу выше и в выжимку ГДД.

Golden-тест `SkillCoverageGoldenTests.EverySkillRow_IsReadableByServer` падает, если в листе появился скилл с неизвестным условием или действием.

## Проверка при публикации конфигов

`SkillComponentValidator` разбирает `triggers` и `actions` каждой строки и отдаёт результат в диалог публикации:

| Что нашли | Как сообщаем |
| --- | --- |
| неизвестное условие или действие | ошибка: публикация не проходит, иначе скилл молча ничего не делает |
| заполнены только `triggers` или только `actions` | ошибка |
| запись не разбирается (нет `имя:[...]`) | ошибка |
| незнакомый параметр у известного компонента | предупреждение |
| запятая внутри `{}` | предупреждение про разделитель третьего порядка |
| аргументы без `{}` | предупреждение |

Строки старого формата (`type`, `proc_order`, `parameters`) валидатор не трогает — для них работает прежняя проверка `EffectParametersValidator`. Имена условий и действий валидатор и боевые реестры берут из одного источника, расхождение ловит `EffectRegistryConsistencyTests`.
