# Нагрузочное тестирование

`tools/Lewdventure.Server.LoadTest` гоняет `replay` (или `simulate`) по всем позитивным golden-кейсам против запущенного сервера и сверяет каждый ответ с эталоном. Проверяет сразу пропускную способность и то, что под нагрузкой бой не меняется.

## Запуск

Сервер без rate limit (Local, compose.local или окружение с `RateLimit__Enabled=false`):

```bash
dotnet run -c Release --project tools/Lewdventure.Server.LoadTest -- \
  --target http://localhost:5000 --concurrency 16 --duration 30 --warmup 3
```

| Параметр | По умолчанию | Описание |
| --- | --- | --- |
| `--target` | `http://localhost:5000` | адрес публичного порта |
| `--cases` | ищется вверх от текущей папки | путь к `Golden/Cases` |
| `--endpoint` | `replay` | `replay` или `simulate` (для `simulate` сверка выключается) |
| `--concurrency` | `16` | число параллельных воркеров |
| `--duration` | `30` | длительность замера, секунды |
| `--warmup` | `3` | прогрев перед замером, секунды |
| `--rps` | `0` | целевой RPS на все воркеры, `0` — без ограничения |
| `--max-error-rate` | `0.01` | допустимая доля ошибок |
| `--max-p95-ms` | `0` | порог p95, `0` — без порога |
| `--no-verify` | — | не сверять ответы с эталонами |

Ошибка — любой ответ не `200`, сетевое исключение или несовпадение с эталоном.

Код выхода: `0` — PASS, `1` — FAIL по порогам, `2` — неверные параметры или нет кейсов.

## Сценарий игроков

`--scenario players` гоняет не бой, а полный путь клиента против сервера с Mongo и авторизацией. Каждый виртуальный игрок:

1. `POST /api/auth/device` с собственным `deviceId` (`<device-prefix>-<id прогона>-N`), получает токен;
2. `GET /api/player/profile` и `GET /api/config/bundle` (повторный бандл — с `If-None-Match`);
3. по кругу: `GET /api/run/current`, при 404 — `POST /api/run/start`; дальше шаги забега: `advance` с `battleDelivery = seed`, на бою — пауза «просмотра» и `battle/finish`, на выборе — `choose` (первые варианты, на развилке — случайная кнопка), после конца забега — новый забег;
4. раз в `--analytics-every` секунд — пачка из пяти событий `loadtest_ping` в `/api/analytics/events`.

Между шагами — пауза `--think-ms` со случайным разбросом ×0,5…1,5. Игроки стартуют равномерно за `--ramp` секунд; замер идёт `--duration` секунд после разгона.

```bash
dotnet run -c Release --project tools/Lewdventure.Server.LoadTest -- \
  --scenario players --target http://localhost:5000 \
  --players 1000 --ramp 60 --duration 120 --think-ms 3000 --battle-watch-ms 8000 --analytics-every 20
```

| Параметр | По умолчанию | Описание |
| --- | --- | --- |
| `--scenario` | `replay` | `replay` — бой по golden-кейсам, `players` — виртуальные игроки |
| `--players` | `100` | число виртуальных игроков |
| `--ramp` | `30` | за сколько секунд стартуют все игроки |
| `--think-ms` | `3000` | пауза между шагами |
| `--battle-watch-ms` | `8000` | «просмотр» боя перед `battle/finish` |
| `--analytics-every` | `20` | интервал отправки аналитики, `0` — не слать |
| `--story-level` | `1` | уровень сюжета для забегов |
| `--device-prefix` | `loadtest` | префикс `deviceId` созданных аккаунтов |

Отчёт — по каждой ручке: запросы, rps, p50/p95/p99/max, коды ответов; итог — ошибки (5xx и сеть, 429, 409), забеги и бои. 404 у `run.current` — норма (забега нет).

Учитывать:

- Все виртуальные игроки идут с одного IP, а вход (`/api/auth/*`) ограничен по IP (`RateLimit:Auth`, 60 в минуту). Для 1000 игроков с одной машины этот лимит на время теста поднимают (`RateLimit__Auth__PermitLimit`); остальные лимиты считаются по игроку и не мешают.
- Тест создаёт настоящие аккаунты, профили, забеги, журнал и события аналитики. Против dev/stage — только вне рабочего времени и с согласия команды; аккаунты потом ищутся по `deviceId` с префиксом. Против prod не запускать.
- Новые игроки без прокачки почти всегда проигрывают первый бой, поэтому забеги короткие и `run/start` идёт часто — нагрузка выше, чем у живых игроков с длинными забегами.

### Результаты 2026-10-18

Release-сборка, Development-настройки, локальная Mongo 8 (один узел, кэш WiredTiger 256 МБ), API и Mongo прибиты к ядрам `taskset` как на dev (`compose.dev.yaml`: по одному ядру). Генератор нагрузки — на отдельных ядрах. ClickHouse не подключён: аналитика принималась, но не писалась.

| API | Игроков | rps | p50 `advance` | p95 `advance` | p99 `advance` | Ошибки |
| --- | --- | --- | --- | --- | --- | --- |
| 1 ядро | 500 | 195 | 4,6 мс | 8,9 мс | 19 мс | 0 |
| 1 ядро | 1000 | 349 | 9 мс | 1594 мс | 1916 мс | 0 |
| 2 ядра | 1000 | 376 | 4,3 мс | 17 мс | 56 мс | 0 |

Одно ядро API — предел около 300 rps: на 1000 игроков сервер не падает и не отвечает ошибками, но запросы стоят в очереди к процессору до 1,5–2 с. Mongo на одном ядре не была узким местом, её память выросла до ~575 МБ при лимите dev 768 МБ. Узкое место dev на 1000 игроков — процессор API.

## Когда запускать

- CI: `docker-smoke` прогоняет 15 секунд на 8 воркерах с `--max-error-rate 0` против контейнера.
- Вручную: перед релизом изменений в симуляции, DI или хосте; сравнить с ориентиром выше.
- Против stage — только с отключённым rate limit на время теста и вне рабочего времени геймдизайнера; против prod не запускать.
