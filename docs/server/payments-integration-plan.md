# План интеграции покупок Steam и Nutaku

Исследование публичной документации на 15 ноября 2026 года. План исходит из релиза с внутриигровыми покупками в Steam и формата **F2P DL Client для Windows** в Nutaku. Тип публикации Nutaku нужно подтвердить первым делом. Для Browser и Mobile меняется клиентский сценарий GI2, при этом серверный обработчик платежей общий. Для Premium DL документация описывает самостоятельную платную сборку без интеграции с платформой. Если Steam продаёт постоянный доступ через DLC, механизм проверки владения нужно рассмотреть отдельно от микротранзакций. [Типы игр Nutaku](https://nutakudoc.atlassian.net/wiki/spaces/ND/pages/3482386433) · [Steam DLC](https://partner.steamgames.com/doc/store/application/dlc)

## Что можно сделать общим

Рекомендую один серверный контур для каталога, заказов, выдачи, возвратов, сверки и поддержки. Checkout в Steam-сборке идёт через Steam Wallet, в Nutaku-сборке через Nutaku Gold. Сервер определяет канал по подтверждённой платформенной сессии. Клиент получает витрину своего канала и отображает результат из серверного заказа. [Требования Steam к покупкам](https://partner.steamgames.com/doc/features/microtransactions) · [Nutaku GI2](https://nutakudoc.atlassian.net/wiki/spaces/ND/pages/3481993220) · [Nutaku DL Client](https://nutakudoc.atlassian.net/wiki/spaces/ND/pages/3483664391)

Для первого релиза предлагаю один тестовый SKU с предсказуемой выдачей и обратимой наградой, затем небольшой каталог из одного SKU на заказ. Платные права и, если понадобится, платный игровой баланс ограничены каналом покупки. Общий прогресс, привязка обеих платформ к одному `userId` и доступ к уже купленным правам из другой сборки требуют отдельных продуктовых решений. Доступ из другой сборки и перенос платного баланса включаем после письменного подтверждения условий от обеих площадок. Публичные материалы подтверждают правила checkout. Разрешение для конкретной схемы Lewdventure остаётся открытым.

## Steam Wallet

1. Unity получает билет через `GetAuthTicketForWebApi` и дожидается `GetTicketForWebApiResponse_t`. Сервер проверяет билет через `ISteamUserAuth/AuthenticateUserTicket` с ожидаемыми AppID и `identity`, получает SteamID из ответа. Проверку владения приложением добавить, если это требуется выбранной моделью доступа. Платформенная сессия привязана к проверенному SteamID. [Аутентификация и владение Steam](https://partner.steamgames.com/doc/features/auth) · [ISteamUserAuth](https://partner.steamgames.com/doc/webapi/ISteamUserAuth)
2. Сервер получает валюту и страну через `GetUserInfo`, сохраняет цену из каталога и создаёт локальный заказ с уникальным `uint64 orderid` до `InitTxn`. Выставлять цену в поддерживаемой валюте пользователя с нужным шагом суммы. Хранить суммы целыми числами в единицах API и передавать 64-битные идентификаторы в JSON строками. При отсутствии цены SKU скрывается для этой валюты. Publisher Web API Key с правом Microtransactions хранится на сервере. [Steam Implementation Guide](https://partner.steamgames.com/doc/features/microtransactions/implementation) · [ISteamMicroTxn](https://partner.steamgames.com/doc/webapi/ISteamMicroTxn) · [Валюты и шаги сумм](https://partner.steamgames.com/doc/store/pricing/currencies)
3. Игрок подтверждает покупку в Steam Overlay. `MicroTxnAuthorizationResponse_t` служит сигналом проверить заказ. Сервер сверяет владельца заказа и данные провайдера. При `Approved` выполняет `FinalizeTxn`. Выдача начинается после успешного ответа `FinalizeTxn` или подтверждения `Succeeded` через `QueryTxn` или достоверные данные отчёта. При тайм-ауте `InitTxn` или `FinalizeTxn` сохранять исходный ID и восстанавливать состояние через Steam. Создание нового заказа при неизвестном результате способно привести к повторному списанию. При сверке учитывать представление VAT и валюты в ответе Steam. [Порядок интеграции](https://partner.steamgames.com/doc/features/microtransactions/implementation) · [ISteamMicroTxn](https://partner.steamgames.com/doc/webapi/ISteamMicroTxn)
4. Фоновая задача восстанавливает зависшие заказы через `QueryTxn`, в том числе когда Unity закрылась после авторизации. Автоматическую финализацию после потери клиентского ответа проверить в sandbox для in-game flow. Сверять оплаченные и отменённые операции через `GetReport` с устойчивым курсором, перекрытием окна и дедупликацией. Курсор продвигать по `time` последнего изменения после обработки результатов. Короткая страница сама по себе не гарантирует конец выгрузки. Valve рекомендует сверку минимум раз в день. Отдельно обрабатывать `PartialRefund` по состояниям позиций, `Refunded`, `Chargedback` и обе категории fraud refunds. `RefundTxn` использовать для возвратов по решению поддержки, результат сверять с провайдером. Для сверки выплат и комиссий Valve указывает `IPartnerFinancialsService`, отдельно от `GetReport` для игровых прав. [Отчёты и статусы Steam](https://partner.steamgames.com/doc/features/microtransactions/implementation) · [Схема ответов `GetReport`](https://partner.steamgames.com/doc/webapi/ISteamMicroTxn#GetReport)

## Nutaku Gold через Game Integration 2.0

1. Unity выполняет вход через Nutaku GI2 и получает NUGT. Пароль передаётся непосредственно в Nutaku. NUGT хранится на клиенте в защищённом хранилище. Для входа на наш сервер используем `Game Handshake`: Nutaku вызывает наш endpoint с `NutakuS2sKey`, `titleId`, `gameType`, `userId`. После серверной проверки выдаём короткоживущий одноразовый код с обменом на нашу сессию. Подтвердить клиентский сценарий входа, включая пользователей со сторонним логином, которым для DL может потребоваться отдельный пароль Nutaku. [DL Client](https://nutakudoc.atlassian.net/wiki/spaces/ND/pages/3483664391) · [Game Handshake](https://nutakudoc.atlassian.net/wiki/spaces/ND/pages/3482517521)
2. Unity начинает платеж через GI2 с NUGT. Nutaku вызывает наш Game Payment Handler Server (GPHS) через `POST`. Проверяем секрет, ожидаемые `titleId` и `gameType`, Nutaku user ID из S2S-запроса, связь с игроком, `paymentId`, SKU, его имя и цену в Gold, а также признак тестовой операции. Сохраняем неизменяемый заказ по `paymentId` до ответа `200 {"response_code":"ok"}`. Повтор с теми же данными возвращает тот же результат. Если связываем вызов с ранее созданной серверной котировкой, в sandbox проверить перенос непрозрачной ссылки через `message` и привязать её к пользователю, SKU, сроку и каналу. На случай отсутствия `message` проверка по подтверждённому пользователю и действующей серверной цене остаётся обязательной. [GPHS](https://nutakudoc.atlassian.net/wiki/spaces/ND/pages/3482124347) · [DL Client](https://nutakudoc.atlassian.net/wiki/spaces/ND/pages/3483664391)
3. Для DL ответ `next=put` ведёт к подтверждению в Unity и вызову GI2 `PUT`. При `next=flyout` пользователю нужно пополнить Gold на Nutaku и начать покупку заново. В sandbox для отработки `next=put` документация указывает `allowPut=1`. После списания Nutaku вызывает наш GPHS через `PUT` без тела, со ссылкой на `paymentId`. Сверяем сохранённый заказ, атомарно фиксируем выдачу, отвечаем `200` с `response_code: ok` только после коммита. При повторе `PUT` с тем же заказом и подтверждённой выдачей возвращаем тот же ответ. Unity запрашивает статус заказа и обновляет инвентарь с сервера. [DL Client](https://nutakudoc.atlassian.net/wiki/spaces/ND/pages/3483664391) · [GPHS](https://nutakudoc.atlassian.net/wiki/spaces/ND/pages/3482124347)
4. **Критический случай: коммит прошёл, ответ потерян.** GPHS описывает возврат Gold, если Nutaku не получил корректного ответа. Бюджет Nutaku составляет 5 секунд для создания и 30 секунд для завершения. Заложить запас на сеть, зафиксировать попытки ответа, проверять состояние локального коммита при тайм-ауте и регистрировать случаи с неопределённым итогом у площадки. Тестировать разрыв соединения после коммита и согласовать с Nutaku, каким источником подтверждать возврат и когда можно отзывать награду. `GET` статуса пригоден для аварийной проверки с учётом задержки репликации. Обычный возврат не меняет статус Nutaku `paymentId`, и документация не описывает действующий postback о возврате. Для продающих SKU до запуска нужен подтверждённый операционный источник возвратов и порядок обработки расхождений. [GPHS, завершение и возвраты](https://nutakudoc.atlassian.net/wiki/spaces/ND/pages/3482124347)

У GI2 цены в целых Gold. GPHS указывает минимум 10, мягкий предел 30 000 и жёсткий 50 000 Gold. MVP стоит держать в пределах 10–30 000 и проверить выбранные цены и поведение подтверждения в sandbox. [Лимиты GPHS](https://nutakudoc.atlassian.net/wiki/spaces/ND/pages/3482124347)

Ограничивать привязку и checkout по частоте. Проверять повторный чужой заказ, попытку подмены владельца, AppID/TitleID, SKU, цены и окружения. Заранее сверить географию, рейтинг, формулировки офферов и критерии Nutaku. ## Порядок работ

1. **Подтвердить условия площадок.** Получить Steam AppID, права на Steamworks Microtransactions и Nutaku sandbox TitleID, подтвердить тип Nutaku-игры и критерии review. Передать обеим платформам схему «два checkout, один backend» и отдельно описать желаемый доступ к покупкам и платному балансу между сборками. Для Nutaku запросить каналы возвратов, споров и отчётности, окно хранения данных, семантику повторов GPHS, поведение при коммите без ответа и путь эскалации для конкретного `paymentId`. Владелец продукта и финансовой части утверждает первый SKU, правила возврата и процесс сверки выплат, комиссий и валют с отчётами площадок.
2. **Собрать модель на сервере.** Платформенные сессии, котировка и неизменяемый заказ, транзакционная выдача и отзыв, постоянная дедупликация, API статуса. Автоматические сценарии на симуляторах провайдеров и Mongo replica set. В CI использовать имитацию ответов, реальные проходы выполнять в sandbox каждой площадки.
3. **Закрыть два sandbox-сценария с Unity.** Steam Overlay → `FinalizeTxn` → выдача и отзыв по отчёту. Nutaku GI2 → GPHS POST/PUT → выдача, сбой после коммита и сверка по согласованному каналу. Протестировать отмену, истёкший заказ, недостаток средств, запрет покупки, валютный шаг, конфиг, сменившийся между созданием и выдачей, перезапуск клиента и сервера. Дубли, нарушенный порядок событий и параллельные покупки должны сходиться к одному результату на заказ. Отдельно проверить ни разу не полученный GPHS PUT и недоступность отчётности.
4. **Подготовить эксплуатацию и включить продажи постепенно.** Развести ключи, ID, базы и тестовые учётки. Сверить sandbox-выдачу, тестовый возврат и отыграть runbook. Получить review для конкретных сборок и офферов, согласовать доступы поддержки. Затем включить по одному провайдеру и небольшому набору SKU с проверкой сверки и возможности остановить новые заказы. Расширять каталог после подтверждения работы восстановления и возвратов.

**Критерий готовности к платному запуску:** для каждого провайдера тестовая покупка однозначно связывается с заказом и единственной выдачей после повторов и сбоев, а поддержка может обнаружить и закрыть расхождение и возврат по внешнему ID. Продажи на одном канале можно запускать независимо от готовности другого при выполнении его критериев.
