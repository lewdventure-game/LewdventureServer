# Игрок: аккаунт и профиль

Кто такой игрок для сервера, где лежит его прогресс и как клиент с этим работает. Состояние забега и серверный бой — следующие фазы, см. `.ai-factory/plans/player-identity-and-state.md`.

## Аккаунт

Аккаунт анонимный и привязан к устройству: ни почты, ни пароля, персональных данных не собираем.

| Эндпоинт | Метод | Тело | Ответ |
| --- | --- | --- | --- |
| `/api/auth/device` | POST | `{deviceId, clientVersion}` | `{userId, accessToken, accessExpiresAt, refreshToken, refreshExpiresAt}` |
| `/api/auth/refresh` | POST | `{userId, refreshToken}` | то же |

- Повторный вызов `device` с тем же `deviceId` возвращает тот же `userId`: аккаунт не дублируется.
- Access — JWT HS256 с `sub = userId`, по умолчанию на 60 минут. Клиент шлёт его в `Authorization: Bearer`.
- Refresh — случайные 32 байта, в Mongo хранится только sha256. При каждом обмене выдаётся новый, старый перестаёт работать. Срок по умолчанию 90 дней.
- `deviceId` в базе тоже только хэшем, уникальный индекс не даёт двум аккаунтам занять одно устройство.
- Забаненный аккаунт получает 403 на `device` и `refresh`.
- Привязка платформы (Steam, Google Play, Telegram) не реализована, но место под неё есть: `users.identities` с уникальным индексом по `provider + subject`, `userId` при привязке не меняется.

## Профиль

| Эндпоинт | Метод | Требует | Ответ |
| --- | --- | --- | --- |
| `/api/player/profile` | GET | Bearer | профиль, создаётся при первом обращении; без загруженных конфигов — `503`, чтобы аккаунт не создавался без стартового набора |
| `/api/player/loadout` | POST | Bearer | профиль после изменения |
| `/api/player/summon/level` | POST | Bearer | поднять уровень саммона за ресурсы |
| `/api/player/summon/mastery` | POST | Bearer | поднять мастерство саммона за копии и выдать награды уровня |
| `/api/player/summon/skill/level` | POST | Bearer | поднять уровень скилла саммона за ресурсы |
| `/api/player/equipment/level` | POST | Bearer | поднять уровень инстанса снаряжения за ресурсы |
| `/api/player/summon/level/reset` | POST | Bearer | сбросить уровень саммона до первого с возвратом части потраченных ресурсов |
| `/api/player/equipment/level/reset` | POST | Bearer | сбросить уровень снаряжения до первого с возвратом части ресурсов |
| `/api/player/equipment/merge` | POST | Bearer | трансформация снаряжения по редкости |
| `/api/player/characteristics` | GET | Bearer | итоговые характеристики, посчитанные сервером |

Тело `loadout`: `{requestId, characterId, equipment: {слот: instanceId}, summons: [id]}`.

Проверки: персонаж открыт и есть в конфигах, саммонов не больше трёх и все свои, инстанс снаряжения принадлежит игроку, а тип из конфига совпадает с именем слота. Ошибки возвращаются списком в 400.

## Награды

Награды применяет только сервер. Строка формата `тип:id:кол-во,тип:id:кол-во` — та же, что в конфигах, парсер общий с боем (`BattleRewardParser` живёт в `Lewdventure.Server.GameConfig/Rewards`).

| Тип | Что делает с профилем |
| --- | --- |
| `resource:<ключ>:<n>` | прибавляет к `resources[ключ]` |
| `character:<id>:<n>` | первая копия открывает персонажа на 1 уровне прокачки (строка `promote_level = 1` стоит 0 копий, её награды выдаются сразу), остальные идут в `copies`; копии автоматически тратятся на промоуты по листу `Character_promotes` (цена — `copies_to_upgrade` уровня), за каждый промоут выдаются его награды, лишние копии сверх последнего уровня конвертируются по константе `character_overflow_resource` |
| `story:<id>:<n>` | открывает сцену владельца награды: из промоута персонажа — в `characters[].unlockedScenes`, из мастерства саммона — в `summons[].unlockedScenes`. Без владельца (например, в награде события) сервер пишет Warning и ничего не открывает |
| `summon:<id>:<n>` | первая копия открывает саммона с уровнем 1 и мастерством 1 и выдаёт награды строки `mastery_level = 1` из `Summon_masteries`, остальные идут в `copies`; когда мастерство саммона уже максимальное, лишние копии конвертируются по константе редкости (`rare/epic/legendary/mythic_summon_overflow_resource`) |
| `equipment:<id>:<n>` | создаёт `n` инстансов первого уровня с собственным `instanceId` |
| `account:<флаг>:<n>` | прибавляет к `flags[флаг]`, например `start_perk_choice_single` |
| `bonus:<id>:<n>` | бонус на аккаунт: `n` складывается в `bonuses[id].count`, если у бонуса в `Bonuses` стоят только `permanent` и/или `if_equipped`. Режимы забега (`end_of_game`, `end_of_battle`, `next_battles`, `first_turns`, `every_turn`) на аккаунт не выдаются — Warning и пропуск, по ГДД они живут только внутри забега |
| `status:*` | профиль не меняет: статус живёт внутри забега |

Каждое начисление пишет запись в `player_ledger` (что, кому, за что, какой `requestId`, какой `rev`). Повтор с тем же `requestId` не начисляет второй раз.

### Прокачка саммонов

`{summonId, requestId}` (у скилла ещё `skillId`), всё считает сервер по конфигам (ГДД 2026-10-04):

- **уровень** — строка `Summon_levels` с `pattern_id = level_pattern_id` саммона и `level` = уровень, **на который** он переходит; ресурсы (`summon_lvl`, на рубежах `summon_break`) списываются из профиля. Мастерство уровень не ограничивает, потолок — последняя строка набора;
- **сброс уровня** — уровень → 1, каждый потраченный ресурс возвращается по `summon_level_reset_coeff`; мастерство и уровни скиллов остаются;
- **мастерство** — списывает `copies_to_upgrade` копий из строки `Summon_masteries` для следующего уровня и выдаёт награды этого уровня (`reward_types/ids/values`, `story` открывает сцену саммона);
- **скилл** — `skillId` из `Summons.skill_ids`; строка `Skill_promotes` с `pattern_id = skill_upgrade_ids[i]` и `level` = уровень, на который переходит скилл. Нужны открытый по `mastery_for_skills` скилл и уровень саммона не ниже `level_to_unlock`. Уровни хранятся в `summons[].skillLevels` по порядку `skill_ids`, отсутствующее значение = 1.

Каждое списание пишется в журнал отрицательной суммой, `requestId` защищает от повторного применения.

### Уровни снаряжения

`{instanceId, requestId}`. Стоимость читается из конфига предмета: `lvlup_types` и `lvlup_values` — параллельные списки через `;`, элемент с индексом `N-1` описывает переход **с уровня N на N+1**, длина списка = максимальный уровень. Тип записывается либо ключом ресурса (`equip_lvl`), либо с префиксом (`resource:equip_break`); другие типы отклоняются с внятной ошибкой.

Лист `Equipments` сейчас пуст, поэтому правило проверено юнит-тестами на подставном конфиге, а не на живых данных. Как только геймдизайнер заполнит колонки, стоит сверить формат: если в таблице окажется другая раскладка, меняется одна функция `EquipmentProgressionRules`.

Трансформация (`merge_group`, `merge_requirements`) не реализована.

Состояние сюжетного забега и серверный бой описаны в [runs.md](runs.md).

## Админские ручки

Только ops-порт и `X-Admin-Key`, для поддержки и отладки.

| Эндпоинт | Метод | Что делает |
| --- | --- | --- |
| `/admin/player/{userId}` | GET | профиль игрока |
| `/admin/player/{userId}/ledger` | GET | последние записи журнала, `?limit=` |
| `/admin/player/{userId}/grant` | POST | `{rewards, reason, requestId}` — начислить награды строкой |
| `/admin/player/{userId}/export` | GET | выгрузка всех данных игрока: аккаунт, профиль, забеги, журнал |
| `/admin/player/{userId}` | DELETE | удаление всех данных игрока, требует `?confirm=<userId>` |

### Характеристики

`GET /api/player/characteristics` считает те же числа, что использует бой: сервер собирает юнита из профиля (персонаж с прокачками, надетая экипировка, саммоны) и активного забега (перки, бонусы, текущее здоровье) и прогоняет через боевой `UnitStateBuilder`. Клиент ничего не присылает и ничего не считает сам, поэтому HUD не может разойтись с боем.

Поля ответа совпадают с боевыми: `health`, `maxHealth`, `damage`, `attackMultiplier`, `armor`, `defence`, `evasion`, `criticalChance`, `criticalMultiplier`, `combo1Chance`, `combo2Chance`, `comboMultiplier`, `counterChance`, `counterMultiplier`, `energy`, `energyGain`, `maxEnergy`, `skillMultiplier`, `vampyrism`, `healingBoost`.

Клиентская фича характеристик ходит в несуществующий `POST api/character/characteristics` — её нужно перевести на этот эндпоинт. Команда боя `SetCharacteristics = 21`, которую ждёт клиент, сервером пока не отправляется: это изменение battle script, его делаем отдельно и осознанно.

## Хранение

| Коллекция | Id | Содержимое |
| --- | --- | --- |
| `users` | `usr_<32 hex>` | устройства, привязки, статус аккаунта |
| `player_profiles` | `userId` | ресурсы, персонажи, саммоны, снаряжение, лоадаут, сюжет, флаги |
| `player_ledger` | uuid | журнал выдач и трат |
| `idempotency` | `userId:requestId` | результат уже применённого запроса, TTL 48 часов |

Профиль — один документ на игрока, поэтому обновляется атомарно без транзакций.

### Что хранится, а что считается

Храним только входные данные: копии, уровни, потраченные ресурсы. Характеристики, множители и бонусы считаются из конфигов на лету — иначе ребаланс таблиц потребовал бы миграции всех игроков, а числа в профиле разошлись бы с тем, что считает бой.

Исключение — уже применённые прокачки (`promoteLevel` персонажа, уровни и мастерство саммонов, уровни скиллов): их фиксируем фактом, иначе подорожание прокачки в таблице откатило бы игроку полученный уровень.

Ресурсы — словарь `{ключ: целое}` с теми же ключами, что в наградах конфигов (`soft_money`, `hard_money`, `summon_lvl`, `summon_break`, `harem_points`, …). Новая валюта в таблице не требует ни миграции, ни кода. Дробные значения в экономике не используются.

Снаряжение — инстансы с собственным `instanceId`: два предмета одного конфига различаются уровнем и `mergeNumber`. Персонажи и саммоны — по `configId`, копии просто счётчик.

### Версия и идемпотентность

- У профиля есть `rev`. Запись идёт фильтром по `{_id, rev}`; если версия не совпала, сервер отвечает 409, клиент перечитывает профиль и повторяет действие.
- Мутирующие запросы принимают `requestId`. Повтор (ретрай на плохой сети) не применяется второй раз: сервер возвращает текущий профиль. Записи живут 48 часов и удаляются TTL-индексом.

## Настройка

| Ключ | По умолчанию | Описание |
| --- | --- | --- |
| `Auth:Enabled` | `false` | включает `/api/auth/*` и `/api/player/*` |
| `Auth:SigningKey` | пусто | ключ подписи JWT, минимум 32 символа, только через env или secrets |
| `Auth:Issuer` | `lewdventure-server` | issuer токена |
| `Auth:Audience` | `lewdventure-client` | audience токена |
| `Auth:AccessTokenMinutes` | `60` | срок access-токена, 5–1440 |
| `Auth:RefreshTokenDays` | `90` | срок refresh-токена, 1–365 |

Аккаунты требуют Mongo: при `Mongo:Enabled=false` эндпоинты отвечают 503. Ключ подписи разный на каждое окружение; при его смене все выданные access-токены перестают работать, клиенты молча перелогинятся по refresh, а refresh переживёт ротацию, потому что не подписан ключом.

Локально всё включено в `compose.local.yaml` с ключом для разработки.
