## 1. Подтверждение боя: `battle/finish`

### Зачем

ГДД: игрок может сдаться прямо посреди боя, а награды за бой выдаются, только когда игрок досмотрел его до конца. Раньше `advance` на бою сразу выдавал награды, опыт и засчитывал этап — сдача во время просмотра уже ничего не отменяла, а на последнем бою уровень засчитывался пройденным.

### Как теперь

```text
advance (этап — бой)
  → сервер считает бой, сохраняет результат «в ожидании»
  ← run.battlePending = true, step.eventType = "fight", step.battleInput (или battle)
    наград, опыта, levelUps нет; stageIndex не сдвинут; run.status = "active" даже при поражении

клиент проигрывает бой

  ├─ досмотрел до конца → POST /api/run/battle/finish {runId, requestId}
  │     ← run.battlePending = false
  │       step.eventType = "fight", appliedRewards, experienceGained, levelUps,
  │       runFailed (поражение) / runCompleted (последний этап), profileRev
  │       run.currentHealth, run.bonuses, run.perks, run.pendingChoice — после боя
  │
  └─ сдался → POST /api/run/abandon (как сейчас)
        ← run.status = "abandoned"; бой отброшен: ни наград, ни опыта, этап не засчитан
```

Пока бой не подтверждён, `advance` и `choose` отвечают `400` «Run waits for battle finish.».

Запрос `battle/finish`:

```json
{ "runId": "run_…", "requestId": "<новый guid на шаг>" }
```

`requestId` — как у `advance`: новый на шаг, тот же при ретрае после обрыва связи. Повтор с тем же `requestId` отвечает текущим забегом с `"replayed": true` и без `step` — тогда как и сейчас: перечитать профиль и показать состояние. `409` — как у `advance`: перечитать `current` и повторить один раз.

### Что сделать на клиенте

1. **Маршрут.** `Core/Servers/ApiRoutes.cs`: `RunBattleFinish = Run + "/battle/finish"`.
2. **Поле ответа.** `Game/Servers/RunResponse.cs` / `IRunResponse.cs`: `bool BattlePending` (json `battlePending`).
3. **Вызов API.** `Game/Servers/RunApi.cs` / `IRunApi.cs`: `FinishBattle(string runId)` по образцу `Advance` — липкий `requestId`, флаг «запрос в полёте», ретрай с тем же id при обрыве сети, обработка `409` через `Current()`. Ключ действия добавить в `KeepId` / `DropId` / `DropBusy`.
4. **После просмотра боя.** Сейчас результат забега читается в `Game/Battles/States/BattleResultState.Enter` (`SnapServerTotals`, дальше победа → `ShowEndPhrase` или поражение → `PresentLoss`). Нужно до этого:
   - если стоит `BattleFlags.Surrendered` — ничего не звать: `RunSurrenderService` уже отправил `abandon`, сервер бой отбросил;
   - иначе — `FinishBattle(run.RunId)`, ответ запомнить как текущий забег (`RunPresenter`: `_run = response`), применить `_runApply.Apply(response)` и только потом идти в существующую логику `Enter` (снапшот ХП, награды, перки, победа/поражение). Исход боя для показа брать по-прежнему из проигранного скрипта; `runFailed` / `runCompleted` / `appliedRewards` / `levelUps` — уже из ответа `battle/finish`.
   - `RunPresenter.Remember` сейчас сбрасывает `battleInput` из шага; в ответе `battle/finish` входа боя нет. Если вход боя ещё нужен после результата — не затирать его ответом `finish`.
5. **Поражение.** Раньше поражение приходило сразу в ответе `advance` (`runFailed`, `status = "failed"`). Теперь `advance` на проигранном бою отдаёт `status = "active"`, а `failed`, `isNewRecord` и `rewardTotals` придут в ответе `battle/finish`. Экран поражения (`BattleResultState.ShowDefeatPanel`, `RunPresenter.ShowRewardTotals`) должен открываться после ответа `finish`.
6. **Сдача.** `RunSurrenderService` менять не нужно: `abandon` во время боя теперь корректно отбрасывает бой. Кнопку «сдаться» на время боя прятать не нужно.

## 2. Возобновление забега с `battlePending`

Если игрок закрыл игру во время боя, `GET /api/run/current` вернёт забег с `battlePending: true` и **без** `step`. Бой заново не показывать — сразу `battle/finish` и показать результат как после боя.

Сейчас `RunPresenter.Present` при `step == null` зовёт `Continue()` → `advance` → сервер отвечает 400. Нужно в начале `Present` (после проверки `ConfigVersion`):

```text
если run.battlePending и run.step == null:
    FinishBattle → запомнить ответ → применить RunApply →
        если поражение (runFailed / status "failed") → ShowDefeat
        иначе → показать награды шага (ShowStepRewards) и продолжить как после боя (ContinueAfterStepRewards)
```

Важно: в ответе `finish` `step.eventType = "fight"`, поэтому повторный `Present()` на нём попытается запустить бой без входа. Поэтому после `finish` при возобновлении звать не `Present()`, а показ наград и продолжение.

## 3. Промоут персонажа по кнопке

ГДД: повторки персонажа копятся на аккаунте и сами ничего не прокачивают; игрок вкладывает их кнопкой в меню прокачки (как звёздность). Раньше сервер промоутил автоматически при получении копий.

Теперь:
- `profile.characters[].copies` копятся; сами тратятся только шаги с `copies_to_upgrade = 0` (открытие персонажа на уровень 1);
- `POST /api/player/character/promote` `{ "characterId": 1, "requestId": "<guid>" }` → профиль целиком. Списывает `copies_to_upgrade` следующего уровня из `Character_promotes`, поднимает `promoteLevel`, выдаёт награды уровня (сцены, бонусы, ресурсы). Копии сверх максимального уровня превращаются в `character_overflow_resource`;
- ошибки `400`: персонаж не открыт, уже максимальный уровень, не хватает копий, идёт забег; `409` — параллельная запись профиля.

Что сделать:
1. `Core/Servers/ApiRoutes.cs`: `PlayerCharacterPromote = Player + "/character/promote"`.
2. `Game/Servers/ProfileApi.cs` / `IProfileApi.cs`: `PromoteCharacter(int characterId)` — копия `RaiseSummonMastery` (тело `{characterId, requestId}`).
3. `Game/Locations/Screens/ProgressionScreen/ProgressionScreen.cs`: кнопка по образцу `_raiseMasteryButton` / `OnRaiseMasteryClicked`, для выбранного персонажа (`_selectedCharacterId`). Активна, если `copies >= copies_to_upgrade` следующего уровня (`ServerCore.Configs.CharacterPromotes.TryGet(mapper.PromoteId, promoteLevel + 1, …)`), уровень не максимальный и нет активного забега. Кнопку в префабе завести в редакторе.

## 4. Во время забега сетап и прокачка закрыты

ГДД: игрок заходит в забег с готовым сетапом юнитов и выходит с ним же; бои забега идут на тех данных, с которыми в него вошли.

Пока в профиле есть `story.currentRunId`:
- `POST /api/player/loadout` с другим персонажем, другим списком саммонов (порядок важен) или другим снаряжением — `400` «Character / Summons / Equipment cannot be changed during run …». Тот же сетап отправить можно;
- вся прокачка — `400` «Progression is locked during run …»: `summon/level`, `summon/level/reset`, `summon/mastery`, `summon/skill/level`, `equipment/level`, `equipment/level/reset`, `equipment/merge`, `character/promote`.

Что сделать: в `ProgressionScreen.RefreshButtons` выключать `_applyLoadoutButton` и все кнопки прокачки (и новую кнопку промоута), если `story.currentRunId` не пустой. Иначе `400` уводит клиент в экран ошибки (`ProfileApi` → `IErrorState`).

## 5. Уровни забега за последней строкой `Exp_levels_patterns`

ГДД (ответ ГД): за последней строкой повторяется последняя. Сервер так и считает: порог опыта и пресеты перков берутся из последней строки, уровни растут дальше. Перки на повышении — из строки достигнутого уровня (переход 1 → 2 берёт строку уровня 2).

В ядре есть `ServerCore.Configs.ExperienceLevelPatterns.TryGetOrLast(patternId, level, out row)`: точная строка, а если её нет — последняя строка паттерна не выше уровня.

Что сделать: `Game/Runs/Services/RunProgressService.cs` — в расчёте «опыта до следующего уровня» заменить `TryGet` на `TryGetOrLast`. Сейчас за последней строкой там ошибка в логе и `0`.

## 6. Перки и группы перков как награда

Новые типы наград в событиях (обычное, развилка, бой) и в наградах перков: `perk:<id>:<кол-во>` и `perk_group:<id>:<кол-во>`. Действуют только внутри своего забега.

- `perk` — перк сразу добавляется в `run.perks` (с учётом `multiple_picks`; если перк — `reward`, выдаются и его награды). В шаге: `appliedRewards` запись `{ "type": "Perk", "id": <perkId>, "count": <сколько добавлено> }`.
- `perk_group` — в очередь ставится выбор перков из группы. В шаге: `{ "type": "PerkGroup", "id": <groupId>, "count": … }`, а в забеге `pendingChoice.kind = "perk"` — тот же выбор, что на повышении уровня. Порядок выборов: стартовые группы → группы из наград → повышения уровня.

Что сделать: ничего обязательного — выбор приходит обычным `pendingChoice`, перк — в `run.perks`, существующий поток это покажет. По желанию — показать награду: `RunPresenter.ShowRewardAt` сейчас пропускает незнакомые типы (`Reward type skipped`); добавить ключи `Perk` / `PerkGroup` в `Keys` и показать строку или иконку перка.

## 7. КОМБО_2_МН

ГДД вернул два множителя комбо: КОМБО_1_МН у первого комбо-удара, КОМБО_2_МН у второго. Бой считает ядро, клиенту ничего не надо. Для отображения:
- `GET /api/player/characteristics` — новое поле `combo2Multiplier` (`comboMultiplier` — КОМБО_1_МН);
- в ядре — `Combo2Multiplier` в характеристиках, `IEnemyMapper.Combo2Multiplier` у мобов, `BonusType` 59–61 (`combo_2_multiplier_local/perk/global`).

Если HUD характеристик (`Game/Characteristics`: `CharacteristicSnapshot`, `CharacteristicType`) должен показывать второй множитель — добавить поле и тип.

## 8. `skin_name` у персонажа и саммона

В листах `Characters` и `Summons` появилась колонка `skin_name` — id префаба боя в Unity, как у мобов. В ядре: `ICharacterMapper.SkinName`, `ISummonMapper.SkinName` (пусто, если колонки нет). `art_name` у саммонов остался (бандл карточки). Использовать, когда визуал боя будет назначаться через конфиг.

## Что изменилось в бою (для QA, клиенту ничего делать не надо)

- КОМБО_1_МН и КОМБО_2_МН раздельные.
- БРОНЯ округляется вниз.
- Вампиризм лечит от реально снятого ХП, урон сверх остатка ХП цели не считается.
- После воскрешения заканчивается ход всей стороны, чей ход идёт: в бою с двумя врагами, если первый убил героя и тот воскрес, второй враг уже не бьёт — ходит герой.
- Статус урона (ожог, яд) от погибшего наложившего продолжает тикать по его статам.
- Воздух и вода снимают только обычные ожог и яд, усиленные остаются.
- `set_bonus` скиллов и `bonus_change`: каждая выдача — отдельный стак со своим сроком (`work_mode`); бонусы, живущие дольше боя, после победы переходят в забег (`run.bonuses`).
- Срок любого бонуса — строго по `work_mode`: бонус с `permanent` / `if_equipped` из события забега или из боя уходит на аккаунт (`profile.bonuses`, в шаге — `appliedRewards` с типом `Bonus`, профиль перечитать по `profileRev`), остальные живут в забеге. По ГДД иконка статуса показывает число действующих стаков, а исчезает вместе с последним.
- Константы `max_health_base` и `armor_base` (вместо `health_base` / `defence_base`). В клиенте `Game/Common/ConstantKeys.HealthBaseKey = "health_base"` сейчас не используется; если начнёт — брать новое имя.

## Проверка после интеграции

1. Новый забег, бой, досмотреть — награды и опыт приходят после боя, забег идёт дальше.
2. Бой, нажать «сдаться» посреди — экран поражения, в профиле нет наград за этот бой, рекорд этапа не засчитан.
3. Закрыть игру во время боя, зайти снова — бой не повторяется, показан результат, забег продолжается.
4. Проигранный бой — экран поражения после досмотра, `isNewRecord` и итоги корректны.
5. Последний бой уровня, досмотреть — победа, уровень открыт; сдаться на последнем бою — уровень не засчитан.
6. Во время забега кнопки сетапа и прокачки неактивны; после забега — активны.
7. Набрать копий персонажа — промоут кнопкой, растёт `promoteLevel`, приходят награды уровня.
8. Прокачаться за последнюю строку `Exp_levels_patterns` — шкала опыта не пустая, выбор перков приходит.
9. Событие с `perk` / `perk_group` в наградах (нужен тестовый лист) — перк в забеге, выбор из группы открывается.
