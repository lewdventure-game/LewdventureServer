# Диалоги и иконки бонусов: интеграция для Unity-клиента

Документ предназначен клиентскому разработчику для интеграции с серверной веткой `andelusiy/dialogues`.

## 1. Статус и область изменений

Серверная часть диалогов и новые поля `Bonuses` реализованы и проверены. Автоматические регрессии не обнаружены: сборка решения успешна, пройдены 480 unit-, 518 golden- и 91 integration-тест, включая MongoDB и HTTP `POST /api/dialogue/complete`.

Изменения обратносовместимы на уровне API и конфигов:

- в ответы профиля и забега добавлено поле `pendingDialogues`;
- добавлен `POST /api/dialogue/complete`;
- в конфиги добавлены домен `Dialogues` и колонки `Story_levels.dialogues_ids` / `dialogues_triggers`;
- в `appliedRewards` добавлен строковый тип `Dialogue`;
- в `IBonusMapper` добавлены `IsDisplayed` и `IconName`;
- формат боя и логика расчёта бонусов не менялись;
- старые снапшоты без новых листов и колонок продолжают загружаться.

Клиентская визуальная часть, Addressables-ассеты и Unity-сцены этой серверной доработкой не менялись. Финальная проверка должна включать совместный прогон клиента и dev-сервера.

## 2. Порядок внедрения

1. Опубликовать лист `Dialogues` и обновлённый `Bonuses` в dev-конфиге. Публикация отклонит неизвестные ID диалогов, неверный граф и отображаемый бонус без `icon_name`.
2. Задеплоить серверную ветку на dev.
3. Обновить серверное ядро у клиента: в `ISharedCore.Configs` должны быть `Dialogues`, а в `IBonusMapper` — новые свойства.
4. Подключить `pendingDialogues`, экран диалога и `dialogue/complete`.
5. Перевести иконки бонусов на `IsDisplayed` / `IconName`.
6. Пройти сценарии из раздела 9 перед передачей в stage/prod.

Старый клиент продолжит работать на конфиге без диалогов и наград `dialogue`: новые поля ответов можно игнорировать. Для диалогового контента и управляемых иконок нужен новый клиент, который также распознаёт тип `Dialogue` в `appliedRewards`.

## 3. Что сервер присылает клиенту

### `pendingDialogues`

Поле присутствует в ответе профиля и в каждом ответе забега:

```json
"pendingDialogues": [
  {
    "launchKey": "level:1:2:on_stage_entered:2",
    "dialogueId": 2,
    "trigger": "on_stage_entered:2"
  },
  {
    "launchKey": "reward:3:5f0c7b1a2d4e",
    "dialogueId": 3,
    "trigger": "reward"
  }
]
```

- `launchKey` — непрозрачный идентификатор запуска. Передавать его обратно без изменений, не формировать на клиенте и не разбирать.
- `dialogueId` — ID набора шагов в `Configs.Dialogues`.
- `trigger` — момент показа. Возможные значения: `on_start`, `on_stage_entered:N`, `on_win`, `on_loss`, `reward`.

В профиле находятся только награды `dialogue:<id>:<n>`. Уровневые запуски приходят в ответах забега. Порядок списка значим: сначала диалоги уровня в порядке `dialogues_ids`, затем награды в порядке выдачи.

Один запуск может прийти повторно в нескольких ответах. Очередь клиента должна исключать дубли по `launchKey`, но не удалять запуск навсегда до успешного `complete`.

### Моменты показа

| `trigger` | Когда клиент показывает диалог |
| --- | --- |
| `on_start` | После загрузки локации, до стартовой фразы и любого взаимодействия с уровнем |
| `on_stage_entered:N` | После нажатия «Дальше», до показа этапа N; ходьбу и анимации уровня поставить на паузу |
| `on_win` | Перед панелью победы |
| `on_loss` | Перед панелью поражения; при сдаче в бою — после сцены проигрыша |
| `reward` | Сразу после получения награды; вне забега — при обработке профиля |

Неподтверждённый `on_stage_entered:N` сервер может повторить после обычного события, выбора перка/развилки или `battle/finish`. В этом случае диалог нужно показать до продолжения соответствующего потока.

Награда в `step.appliedRewards` имеет вид:

```json
{ "type": "Dialogue", "id": 3, "rewardKey": "", "count": 1 }
```

Она означает постановку в очередь, а не сам показ. Для показа использовать соответствующий элемент `pendingDialogues`. В `rewardTotals` такая награда не входит.

## 4. Проигрывание диалога

### Получение шагов

Менеджер доступен как `ISharedCore.Configs.Dialogues` и поддерживает:

```csharp
bool Contains(int dialogueId);
bool TryGet(int dialogueId, int step, out IDialogueStepMapper mapper);
void CopySteps(int dialogueId, List<IDialogueStepMapper> steps);
```

Начинать с `step = 1` через `TryGet(dialogueId, 1, out var step)`. `CopySteps` очищает переданный список и заполняет его шагами диалога. Если лист не опубликован, менеджер пустой — диалогов нет, это штатная ситуация.

Для активного забега использовать конфиг версии `run.configVersion`, закреплённый за забегом. Не подменять шаги свежим снапшотом посреди забега. Для награды вне забега используется текущий снапшот.

### Поля шага `IDialogueStepMapper`

| Свойство | Правило для клиента |
| --- | --- |
| `Id`, `Step` | ID диалога и номер текущего шага |
| `NextSteps` | Пустой массив — конец диалога; без выбора — один следующий шаг; с выбором — по одному переходу на вариант |
| `IsFadeOnStart` | `true` — затемнение перед сменой на этот шаг; на первом шаге — затемнение от исходного экрана |
| `Characters` | Спрайты именно этого шага, без наследования с прошлого; порядок в массиве — порядок отрисовки, позже — ближе к игроку |
| `CurrentCharacterLocName` | Ключ имени говорящего; пусто — скрыть плашку имени |
| `Backgrounds` | Ключи фонов по порядку; пусто — оставить предыдущий фон, на первом шаге — затемнённый экран источника; последний фон зацикливается |
| `Music` | Ключ музыки; пусто — продолжить текущую; при завершении диалога вернуть музыку исходного экрана по правилам ГДД |
| `Sounds` | Оркестры по индексам `Backgrounds`; пустой элемент означает отсутствие звука; пустой массив — оставить прежний оркестр; после последнего шага остановить текущий оркестр без замены |
| `LocalizationKeys` | Индекс 0 — основной текст; индексы 1..N — варианты выбора сверху вниз |
| `TextSpeed` | Скорость печати в символах **в секунду** |

У `DialogueCharacter`:

- `SpriteName` — Addressables-ключ спрайта;
- `ScreenPercent` — горизонтальная позиция центра спрайта, 0–100% ширины экрана.

Тап по экрану сначала допечатывает текст, повторный тап переводит на `NextSteps[0]`. Если есть выбор, тап вне вариантов шаг не меняет. Выбор с номером `pick` переводит на `NextSteps[pick - 1]`.

Переходить к `complete` нужно только после последнего шага (`NextSteps` пуст). Закрытие приложения или выход посередине не считается показом: сервер снова предложит этот запуск.

Проверить заранее наличие Addressables-ключей фонов, спрайтов, музыки, оркестров и ключей локализации. Отсутствие ассета не должно оставлять игрока в заблокированном состоянии без возможности завершить диалог.

## 5. Подтверждение показа

### Запрос

`POST /api/dialogue/complete`, Bearer-авторизация как у остальных player API:

```json
{
  "requestId": "6f1df0d2f0a548c6a6b245c3f7d77a11",
  "launchKey": "level:1:2:on_stage_entered:2",
  "picks": [1, 2]
}
```

- `requestId` — новый уникальный ID для каждого нового подтверждения. Для повтора после таймаута/потери ответа использовать **тот же** ID.
- `launchKey` — точное значение из `pendingDialogues`.
- `picks` — номера выбранных вариантов с 1, в порядке шагов с выбором на фактически пройденном пути. Без выборов передавать `[]`; `null` сервер тоже принимает как пустой список.

Например, если на первой развилке выбран второй вариант, а на следующей — первый, передаётся `[2, 1]`.

### Ответы и обработка

| Ответ | Действие клиента |
| --- | --- |
| `200` | Удалить `launchKey` из локальной очереди и перейти к следующему диалогу/продолжить игру. Ответ содержит актуальный профиль |
| `400` | Не повторять автоматически. Сохранить диагностику: неверный `launchKey` или `picks` не соответствуют графу/конфигу |
| `409` | Повторить позже с теми же `requestId`, `launchKey` и `picks`; соблюдать общую обработку конфликтов профиля |
| `401` | Обновить авторизацию по существующему flow |

Повтор с тем же `launchKey` или непустым `requestId` не меняет профиль повторно и не дублирует аналитику. Сохраняются выборы из первого успешного подтверждения.

Сервер отправляет только событие `dialogue_completed`; отдельного `dialogue_offered` клиенту ждать или имитировать не нужно.

### Повторная доставка при потере ответа

- Повторять операцию забега с прежними `runId` и `requestId`, а не создавать новый запрос.
- `GET /api/run/current` возвращает последний неподтверждённый диалог этапа, пока следующий `advance` не открыл другой этап.
- После завершения забега `current` возвращает `404`; для восстановления `on_win`/`on_loss` повторить завершающее действие с прежними `runId` и `requestId`.
- Если запуск больше не восстанавливается в этом забеге, сервер предложит его при следующем таком же триггере.

## 6. Иконки бонусов

В `IBonusMapper` добавлены:

```csharp
bool IsDisplayed { get; }
string IconName { get; }
```

Правило отображения:

```csharp
var showIcon = bonus.IsDisplayed && !string.IsNullOrWhiteSpace(bonus.IconName);
```

- `IsDisplayed = false` — иконку не показывать.
- `IsDisplayed = true` — загрузить иконку по `IconName` из Addressables.
- Пустой `IconName` при `true` запрещён серверной публикацией новых снапшотов. На старом снапшоте такой случай следует обработать как скрытую иконку и записать диагностическое сообщение, без fallback на вшитое имя.

Что изменить в клиенте:

1. Убрать определение адреса и видимости через вшитый `switch` по `BonusType` (`BonusIconAddress` и аналогичные места).
2. Использовать `Configs.Bonuses.TryGet(bonusId, out var bonus)` и новые свойства во всех местах показа: HUD боя и забега, попап характеристик, награды и другие списки бонусов.
3. Применить тот же фильтр в предзагрузке (`BattlePreloadKeysBuilder` и смежных сборщиках ключей): не запрашивать пустые адреса и ассеты скрытых бонусов, исключить дубли ключей.
4. Не менять логику действия бонуса: новые поля отвечают только за визуал.

В старых снапшотах без `is_displayed` и `icon_name` свойства принимают значения `false` и `""`, поэтому иконки будут скрыты до публикации обновлённого листа.

## 7. Минимальный объём клиентской интеграции

Если клиентская область `Assets/Scripts/Game/Dialogues/` уже реализована, достаточно сверить её с контрактом выше. В противном случае необходимы:

- очередь запусков с dedupe по `launchKey` и моментами показа по `trigger`;
- player шагов конфига с выборами, печатью текста, фонами, спрайтами, музыкой и fade;
- пауза забега на время диалога;
- вызов `complete` с сохранением фактических `picks` и повторами по `requestId`;
- использование закреплённой версии конфига забега;
- обработка отсутствующего домена и ассетов без блокировки игрового потока;
- переход всех иконок бонусов на `IsDisplayed` / `IconName`.

Подходящие места в клиентской архитектуре: `DialogueLauncher`/`DialoguePlayer`, `ProfileApi` или отдельный `DialogueApi`, `RunPresenter`, `RunInitState`/`RunLoopState`, `ConfigSnapshotSync`, сервисы иконок и предзагрузки бонусов.

## 8. Что не нужно делать

- Не читать `launchKey` по частям и не вычислять момент показа из него — использовать `trigger`.
- Не подтверждать диалог при открытии экрана — только после последнего шага.
- Не генерировать новый `requestId` на retry.
- Не считать запуск показанным только локально: источник истины — серверный `complete`.
- Не применять свежий конфиг к шагам активного забега.
- Не показывать иконку только потому, что бонус пришёл в `run.bonuses` или `appliedRewards`.
- Не добавлять отдельный клиентский `dialogue_offered` в ожидании такого события от сервера.

## 9. Приёмочный сценарий

### Диалоги

- Линейный диалог: первый/последний шаг, печать и допечатка текста, `complete` с `picks: []`.
- Ветвление и хаб с циклом: каждый выбор ведёт на правильный `next_step`, `picks` сохраняют порядок.
- Все четыре триггера уровня и сдача во время боя.
- Несколько диалогов в одном ответе: порядок уровень → награды, без параллельных экранов.
- Награда `dialogue` в забеге и в профиле вне забега.
- Повтор `advance` и `current` после обычного события, выбора и `battle/finish`: запуск не теряется и не дублируется в очереди.
- Потеря ответа `complete`, повтор с тем же `requestId`: один `completed`, один набор `picks`.
- Закрытие приложения до `complete`: диалог приходит снова.
- Смена активного снапшота: шаги активного забега остаются на его версии конфига.
- Отсутствующий лист `Dialogues`: игра работает без ошибок и экранов диалогов.

### Иконки

- `IsDisplayed = true`: загружается именно `IconName` во всех UI и предзагрузке.
- `IsDisplayed = false`: иконка отсутствует во всех UI и не попадает в предзагрузку.
- Старый снапшот без новых колонок: нет обращений к Addressables с пустым ключом и нет вшитого fallback.
- Отсутствующий ассет: диагностика без падения экрана или блокировки боя.
