# Покупки Steam и Nutaku

API реализует Steam Wallet и Nutaku Gold через GI2 для F2P DL Client. Каждый заказ содержит один SKU, одну единицу постоянного права и необязательные награды профиля. Сервер хранит снимок цены и состава, выполняет выдачу атомарно и обрабатывает повторы и возвраты.

[Инструкция для Unity-клиента](payments-client.md) — основной клиентский контракт.

## Модель оффера

Оффер задаёт внутренний `Sku`, отображаемое `Name`, постоянный `Entitlement`, необязательные `Rewards`, Steam item ID и цены по валютам, а также цену Nutaku Gold.

Платёжные награды ограничены типами:

- `resource:<ключ>:<положительное количество>` — попадает в `profile.resources`;
- `account:<ключ>:<положительное количество>` — попадает в `profile.flags`.

Персонажи, саммоны, снаряжение, бонусы и диалоги в платёжных `Rewards` запрещены валидацией конфигурации. Для постоянного доступа используется `Entitlement`. Ноль или отсутствующий маппинг цены скрывает оффер на соответствующей площадке.

Пример тестового окружения:

```dotenv
Payments__SteamAppId=123456
Payments__SteamSandbox=true
Payments__SteamPurchasesEnabled=true
Payments__NutakuTitleId=lewdventure-sandbox
Payments__NutakuSandbox=true
Payments__NutakuPurchasesEnabled=true
Payments__Offers__0__Sku=starter-access
Payments__Offers__0__Name=Starter Access
Payments__Offers__0__Entitlement=starter-access
Payments__Offers__0__Rewards=resource:soft_money:100,account:starter_pack:1
Payments__Offers__0__SteamItemId=1001
Payments__Offers__0__SteamPrices__USD=199
Payments__Offers__0__NutakuGold=200
```

App ID, Title ID и SKU в примере не являются боевыми. Секреты передаются отдельно:

```dotenv
Payments__SteamPublisherKey=
Payments__NutakuServerKey=
```

Платёжные маршруты появляются при заданном App ID или Title ID. Требуются авторизация, Mongo replica set и успешное создание индексов. Оба канала по умолчанию sandbox, новые продажи выключены. Отключение `*PurchasesEnabled` скрывает новые офферы, но оставляет обработку существующих заказов, колбэков, отчётов и возвратов. Изменения применяются после перезапуска API.

## Атомарная выдача

В одной Mongo-транзакции фиксируются:

- состояние заказа и внешний transaction/payment ID;
- постоянное право в `payment_entitlements`;
- изменение профиля для `Rewards`;
- запись игрового ledger со стабильным платёжным ID;
- движение `granted` или `reversed` в `payment_movements`.

Игровая 48-часовая идемпотентность в платёжном пути не используется. Повтор одного и того же подтверждения не удваивает ни право, ни награды.

При полном возврате сервер обратно списывает ресурсы и account-флаги только если хватает всего выданного количества. Баланс не может стать отрицательным. Если часть награды уже израсходована, профиль не меняется, право отзывается, заказ становится `Reversed` с `reviewRequired=true` и причиной `reward_recovery_required`.

Оператор затем выбирает `deduct_available` или `rewards_kept`; решение сохраняется в аудите вместе с проверяемой ссылкой на обращение.

## Платформенная идентичность

Device-, Steam- и Nutaku-аккаунты остаются раздельными. Привязки и переноса прав между каналами нет.

`payment_accounts` сохраняет соответствие платформенного subject и игрового `userId`. Если игровой профиль удалён, повторный платформенный вход создаёт пустой пользовательский документ с прежним `userId`. Действующие права сохраняются, а активные награды восстанавливаются по заказам при обращении к платёжному API.

Сброс игрового профиля и ledger также не отменяет покупки. Восстановление использует стабильные ledger ID и не удваивает награды при параллельных запросах. Удалённые заказы и аудит остаются доступны операторской сверке; перед production нужно утвердить сроки хранения и правовое основание сохранения внешних идентификаторов.

## Steam Wallet

Сервер проверяет билет `GetAuthTicketForWebApi` через `AuthenticateUserTicket`, получает валюту через `GetUserInfo`, создаёт уникальный `uint64 orderid`, вызывает `InitTxn`, сверяет `QueryTxn` и завершает одобренную операцию через `FinalizeTxn`.

Фоновая сверка:

- проверяет ожидающие заказы каждые несколько секунд;
- вызывает `GetReport` каждую минуту с устойчивым курсором;
- обрабатывает успех, отказ, полный и частичный возврат, chargeback и fraud-статусы;
- при неопределённой инициализации повторяет `InitTxn` с тем же `orderId`, не создавая второй заказ;
- через сутки без изменения отмечает ожидающий заказ `stale_pending` и прекращает автоматический polling до операторского `retry`.

Несовпадение владельца, цены, item ID или ответа `FinalizeTxn` открывает review. Успешный заказ можно восстановить после потери ответа `FinalizeTxn` через `QueryTxn` или отчёт.

Провайдерские возвраты и chargeback обрабатываются автоматически. `RefundTxn` используется для ручного полного возврата. Steam DLC и финансовая сверка выплат/комиссий не входят в этот контур.

## Nutaku Gold

Game Handshake проверяет S2S key, Title ID и `gameType=dl`, затем создаёт одноразовый код с TTL две минуты. В CMS настраиваются HTTPS URL:

- Game Handshake: `/api/payments/nutaku/handshake`;
- Game Payment Handler: `/api/payments/nutaku/handler`.

GPHS POST проверяет пользователя, SKU, имя, цену, payment ID и test-флаг, затем сохраняет заказ. GPHS PUT атомарно выдаёт покупку после списания Gold. Повторный PUT возвращает тот же результат без повторной выдачи. В live тестовые операции отклоняются.

Тайм-аут, обрыв соединения или неопределённая транзакция выдачи создают `nutaku_completion_uncertain`, аудит и critical alert. Это важно, потому что Nutaku может вернуть Gold, если не получила корректный ответ после серверного коммита.

Обычный возврат не меняет статус Nutaku `purchase`. Поэтому provider-status пригоден только для аварийной диагностики и не доказывает отсутствие возврата. Для production по-прежнему нужен согласованный с Nutaku операционный источник подтверждения возвратов; серверная очередь review и ручной возврат для него готовы.

## Клиентские маршруты

| Метод и путь | Назначение |
| --- | --- |
| `POST /api/auth/steam` | вход по билету Steam |
| `POST /api/auth/nutaku` | вход по одноразовому handshake-коду |
| `GET /api/payments/catalog` | офферы текущего канала, право и структурированные награды |
| `POST /api/payments/steam/orders` | создание или повтор Steam-заказа по `requestKey` |
| `GET /api/payments/orders` | последние 50 заказов текущего аккаунта/канала |
| `GET /api/payments/orders/{orderId}` | состояние, состав и `reviewRequired` своего заказа |
| `GET /api/payments/entitlements` | действующие постоянные права текущего канала |

Точные запросы и клиентские сценарии — в [payments-client.md](payments-client.md).

## Операторские маршруты

Все маршруты доступны только на ops-порту с admin API key. Для изменяющих операций обязателен `reference` — проверяемый номер обращения или записи площадки. `X-Admin-Actor` идентифицирует оператора; без него записывается IP.

| Метод и путь | Назначение |
| --- | --- |
| `GET /api/admin/payments/review` | до 100 заказов, требующих разбора, самые старые первыми |
| `GET /api/admin/payments/by-user/{userId}` | до 200 заказов и действующие права по всем каналам |
| `GET /api/admin/payments/{platform}/{orderId}` | заказ, движения и до 100 событий аудита |
| `POST /api/admin/payments/{platform}/{orderId}/reverse` | подтверждённый возврат Nutaku или запрос `RefundTxn` Steam |
| `POST /api/admin/payments/{platform}/{orderId}/review/resolve` | закрыть review с решением и ссылкой |
| `GET /api/admin/payments/nutaku/{orderId}/provider-status` | аварийная диагностика GI2 |

Тело возврата:

```json
{"reference":"case-123"}
```

Для Steam `204` означает сохранённый отзыв, `202` — неопределённый результат, который сверяется через заказ и отчёт. Запрос, подтверждение и неопределённый результат возврата записываются в `payment_audits`.

Тело закрытия review:

```json
{"reference":"case-123","resolution":"confirmed"}
```

Допустимые решения:

- `confirmed` — расхождение разобрано, изменения профиля не требуются;
- `retry` — вернуть ожидающий Steam-заказ в фоновую обработку ещё на сутки;
- `rewards_kept` — подтверждённый возврат, но выданные награды оставлены игроку;
- `deduct_available` — списать доступный остаток наград без отрицательного баланса и закрыть случай.

## Наблюдаемость

Health check `payments` подключён к `/health` и `/health/ready`:

- `warn`, если review queue непуста;
- `warn`, если Steam settlement report не обновлялся более десяти минут;
- данные содержат число review, курсор, последнее успешное обновление и ошибку отчёта.

Бизнес-review не делает процесс неготовым и не блокирует новые заказы. Открытие review дополнительно публикует critical alert, закрытие — resolved alert.

Метрики Meter `Lewdventure.Server`:

- `lewdventure.payments.settlements`;
- `lewdventure.payments.reviews`;
- `lewdventure.payments.provider.errors`.

## Коллекции

- `payment_orders` — неизменяемые условия, состояние, ошибки и review;
- `payment_entitlements` — действующие права по одному на заказ;
- `payment_movements` — выдача и отзыв;
- `payment_accounts` — устойчивое соответствие платформенного subject и `userId`;
- `payment_login_codes` — одноразовые коды с TTL;
- `payment_report_cursors` — курсор и здоровье отчёта Steam;
- `payment_audits` — попытки возвратов и решения операторов.

## Условия production

До включения реальных продаж необходимо:

1. Пройти клиентские sandbox-сценарии обоих каналов, включая потерю ответа после выдачи и возврат.
2. Подтвердить Nutaku-источник возвратов и назначить владельца review queue.
3. Настроить алерты и проверить runbook остановки новых продаж, retry и возвратов.
4. Утвердить SKU, правила израсходованных наград, хранение финансовых данных и сверку выплат/комиссий.
5. Получить review площадок для конкретных сборок и офферов.
6. Для live явно задать `SteamSandbox=false` и/или `NutakuSandbox=false`, использовать отдельные ключи и базы и включать по одному каналу с небольшим набором SKU.
