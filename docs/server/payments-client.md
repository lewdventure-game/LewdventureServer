# Интеграция покупок Steam и Nutaku для Unity-клиента

Документ для клиентского разработчика. Сервер реализует Steam Wallet и Nutaku Gold через GI2 для F2P DL Client. Платёжные ключи, проверка цены, завершение транзакции, выдача и возврат находятся только на сервере.

Серверный статус: готово к совместному sandbox-тестированию. До production нужны успешные сценарии этого документа на реальных sandbox-аккаунтах и включение конфигурации площадок.

## 1. Главные правила

- Успех покупки — только серверное состояние `Granted`. Колбэк Steam Overlay или завершение GI2 — лишь сигнал запросить заказ заново.
- Клиент никогда не вызывает Steam `FinalizeTxn`, не начисляет ресурсы и не записывает результат покупки локально.
- Все идентификаторы заказов и `paymentId` передаются в JSON строками. Не преобразовывать их в `long` или `double`.
- Все суммы — целые числа. Steam использует минорные единицы валюты и требуемые площадкой шаги; Nutaku использует целые Gold.
- Платёжные SDK вызываются только в Steam-/Nutaku-сборке соответствующей площадки.
- Device-, Steam- и Nutaku-аккаунты раздельны. Автоматической привязки и переноса прогресса или прав между ними нет.
- Взаимодействие с игровым сервером — только HTTPS. Publisher key, Nutaku S2S key и NUGT на игровой сервер не отправляются.

## 2. Общая серверная модель

Один заказ содержит один SKU и выдаёт:

- одну единицу постоянного права `entitlement`;
- необязательный набор наград профиля `rewards`.

Поддерживаются награды `resource` и `account`. Ресурсы появляются в `profile.resources`, account-награды — в `profile.flags`. Состав и цена фиксируются в заказе и не меняются при последующем изменении каталога.

Для запросов игрока нужен заголовок:

```http
Authorization: Bearer <accessToken>
```

Платформенный вход возвращает только access-токен. Refresh-токена у него нет: после `401` или истечения `accessExpiresAt` клиент повторяет вход площадки. Bearer действует и в игровом API, и в магазине своего канала.

## 3. Вход Steam

### 3.1. Получить билет

1. Инициализировать Steamworks SDK и дождаться готовности Steam API.
2. Вызвать `ISteamUser::GetAuthTicketForWebApi` с identity `lewdventure-server`.
3. Дождаться `GetTicketForWebApiResponse_t` и проверить результат.
4. Передать байты билета на сервер в hex. Регистр hex не важен, пробелы и префикс `0x` не нужны.

Не использовать устаревший сценарий с билетом для игровых серверов вместо `GetAuthTicketForWebApiResponse_t`.

### 3.2. Обменять билет

`POST /api/auth/steam`

```json
{
  "credential": "CAFE0123..."
}
```

Ответ `200`:

```json
{
  "userId": "usr_0123456789abcdef",
  "accessToken": "eyJ...",
  "accessExpiresAt": "2026-11-22T12:00:00Z"
}
```

`400` — билет имеет неверный формат; `401` — Steam не подтвердил билет; `403` — игровой аккаунт заблокирован или относится к QA; `502` — временная ошибка связи со Steam.

Билет и access-токен не писать в аналитику и обычные логи. Токен хранить в защищённом хранилище сборки.

## 4. Вход Nutaku

1. Выполнить вход в Nutaku GI2 и получить клиентский NUGT по DL-инструкции Nutaku.
2. Запустить Game Handshake из клиента GI2.
3. Nutaku сама вызывает серверный `/api/payments/nutaku/handshake`. Клиент не подписывает этот вызов и не знает S2S key.
4. В ответе GI2 проверить `game_rc == 200`. Поле `message` — строка с JSON от игрового сервера:

```json
{"code":"одноразовый-код"}
```

5. Разобрать `message` как JSON и в течение двух минут вызвать игровой сервер.

`POST /api/auth/nutaku`

```json
{
  "credential": "одноразовый-код"
}
```

Ответ — такой же, как у Steam. Код одноразовый: повтор того же кода даёт `401`. Для нового входа выполнить новый handshake. Не отправлять на игровой сервер пароль Nutaku или NUGT.

## 5. Витрина

`GET /api/payments/catalog`

Ответ `200`:

```json
[
  {
    "sku": "starter-access",
    "name": "Starter Access",
    "entitlement": "starter-access",
    "currency": "USD",
    "amount": 199,
    "rewards": [
      { "type": "resource", "key": "soft_money", "amount": 100 },
      { "type": "account", "key": "starter_pack", "amount": 1 }
    ]
  }
]
```

Для Nutaku `currency` равен `GOLD`, а `amount` — цена в Gold. Для Steam валюту и сумму показывать именно из ответа, не формировать цену на клиенте.

Пустой массив — штатный ответ: продажи выключены, валюта не поддерживается или нет доступных офферов. `502` означает временную ошибку получения валюты Steam; витрину можно повторить.

Кнопка покупки должна содержать конкретный снимок `sku`, `currency` и `amount`. Перед запуском новой попытки после изменения витрины нужно обновить эти значения.

## 6. Покупка Steam

### 6.1. Создать или восстановить попытку

Перед checkout создать UUID и сохранить его вместе с SKU до окончательного результата. Это `requestKey`, а не игровой `requestId`.

`POST /api/payments/steam/orders`

```json
{
  "requestKey": "7d64a93e-32df-4d4b-b712-3f3c7a0a44b1",
  "sku": "starter-access",
  "currency": "USD",
  "amount": 199
}
```

Ответ `200`:

```json
{
  "orderId": "10923847560293847560",
  "sku": "starter-access",
  "amount": 199,
  "currency": "USD",
  "entitlement": "starter-access",
  "rewards": [
    { "type": "resource", "key": "soft_money", "amount": 100 },
    { "type": "account", "key": "starter_pack", "amount": 1 }
  ],
  "state": "AwaitingApproval",
  "reviewRequired": false,
  "createdAt": "2026-11-22T11:00:00Z",
  "grantedAt": null,
  "reversedAt": null
}
```

После успешного `InitTxn` Steam сам показывает Overlay. Клиенту не нужно открывать отдельный браузер.

При повторе после тайм-аута, `502`, обрыва или перезапуска использовать **тот же `requestKey` и те же SKU/валюту/цену**. Сервер вернёт исходный заказ и не создаст вторую покупку. Другой набор параметров с тем же ключом даёт `409`.

`503` при создании нового заказа означает, что продажи временно выключены. Уже созданный заказ продолжает обрабатываться.

### 6.2. Обработать Overlay и статус

Подписаться на `MicroTxnAuthorizationResponse_t`. Этот колбэк только запускает немедленное обновление заказа. Даже отказ в колбэке стоит сверить с сервером.

`GET /api/payments/orders/{orderId}`

Во время ожидания опрашивать раз в 2–3 секунды с экспоненциальной паузой после повторных ошибок. Не создавать новый `requestKey` из-за долгого ожидания. После закрытия экрана магазина восстановить заказ по сохранённому `orderId` или через список заказов.

| `state` | Что делать клиенту |
| --- | --- |
| `Created` | Локальная резервация создана, ожидать или повторить checkout с тем же ключом. |
| `Initiating` | Сервер восстанавливает инициализацию Steam. Ожидать. |
| `AwaitingApproval` | Пользователь авторизует заказ в Overlay или сервер ждёт подтверждение площадки. Ожидать. |
| `Granted` | Покупка завершена. Показать успех и синхронизировать права и профиль. |
| `Failed` | Попытка отклонена или завершилась ошибкой. Новую попытку начинать с новым `requestKey`. |
| `Reversed` | Покупка возвращена, право отозвано. Обновить права и профиль. |

`reviewRequired: true` в ожидающем заказе означает ручной разбор. Показать «платёж проверяется», сохранить `orderId` и не запускать другую попытку. Если состояние уже `Granted`, выдача подтверждена; внутренний review не требует повторной покупки.

После `Granted` вызвать:

1. `GET /api/payments/entitlements`;
2. `GET /api/player/profile`;
3. обновить UI из ответов сервера, а не прибавлять `rewards` локально.

## 7. Покупка Nutaku

1. Получить оффер из `/api/payments/catalog`.
2. Передать в GI2 DL payment creation данные выбранного оффера: `skuId = sku`, `name = name`, `price = amount`. Остальные поля оформления и `message` заполняются клиентом по DL-инструкции.
3. Обработать ответ GI2:
   - `next=put` — разрешить подтверждение покупки в клиенте GI2;
   - `next=flyout` — пользователю нужно пополнить Gold на Nutaku, затем начать покупку заново;
   - ошибку показать без локальной выдачи.
4. Nutaku вызывает серверный GPHS `POST`, списывает Gold и вызывает GPHS `PUT`. Клиент не вызывает эти endpoint-ы.
5. Завершение GI2 использовать только как сигнал обновить заказ и инвентарь.

Для опроса использовать `paymentId`, выданный Nutaku:

`GET /api/payments/orders/{paymentId}`

Интерпретация состояний та же. Повторный GPHS `PUT` не создаёт вторую выдачу. Если Nutaku не получила корректный ответ после списания, она может вернуть Gold; спорный заказ сервер отмечает `reviewRequired`. Клиент не должен пытаться «исправить» это повторной покупкой.

В live операции тестовых пользователей сервер отклоняет. Для sandbox использовать тестовые аккаунты и настройки Nutaku, включая `allowPut=1`, если это требуется сценарием GI2.

## 8. История и инвентарь

`GET /api/payments/orders` возвращает последние 50 заказов текущего аккаунта и канала в формате одиночного заказа.

`GET /api/payments/entitlements`:

```json
{
  "starter-access": 1,
  "another-permanent-right": 2
}
```

Это действующие постоянные права текущего канала. При возврате уменьшается только единица, связанная с возвращённым заказом. Не кэшировать словарь как постоянный источник истины.

`GET /api/player/profile` возвращает актуальные `resources` и `flags`. Если профиль был сброшен или удалён, активные платные награды восстанавливаются при обращении к платёжному API. Поэтому при запуске магазина и после повторного входа сначала синхронизировать entitlements, затем профиль.

## 9. Ошибки и повторы

| Код | Поведение клиента |
| --- | --- |
| `400` | Неверный формат запроса или оффер не прошёл проверку. Исправить запрос, не повторять без изменений. |
| `401` | Войти через площадку заново. Для Nutaku получить новый handshake-код. |
| `403` | Канал токена не соответствует магазину либо аккаунт недоступен. Не пытаться обойти другим endpoint-ом. |
| `404` | Заказ не найден или принадлежит другому аккаунту/каналу. Проверить сохранённую сессию и ID. |
| `409` | Ключ повтора использован с другими параметрами, цена изменилась или операция конфликтует. Перечитать витрину/заказ. |
| `429` | Сработал общий player rate limit. Увеличить паузу и не запускать параллельный polling. |
| `502` | Площадка не подтвердила ответ. Повторить с тем же `requestKey` или сначала прочитать заказ. |
| `503` | Временная недоступность или остановка новых продаж. Существующий заказ продолжать опрашивать. |

Повторы должны иметь ограничение по времени и jitter. Приложение может закрыться в любой момент: восстановление делается по серверному заказу, а не по локальному флагу «оплачено».

## 10. Обязательная приёмка с сервером

### Steam

- Вход по настоящему `GetAuthTicketForWebApi` и обновление токена после истечения.
- Overlay → `Approved` → серверный `FinalizeTxn` → `Granted` → одна выдача.
- Повтор checkout с тем же ключом вызывает не более одного `InitTxn` для нормального потока.
- Отмена, недостаток средств, ограничение покупки и неверный шаг валюты.
- Закрытие клиента до и после авторизации; восстановление по `orderId`.
- Потеря ответа сервера и повтор с тем же `requestKey`.
- Полный возврат и chargeback: `Reversed`, право удалено, профиль обновлён.

### Nutaku

- Handshake с разбором `message`, истечение и повтор одноразового кода.
- `next=put`, `next=flyout`, отмена и недостаток Gold.
- Повторы GPHS POST/PUT и перезапуск клиента до/после списания.
- Потеря ответа после серверной выдачи и показ `reviewRequired` без повторной покупки.
- Подтверждённый площадкой возврат: `Reversed`, инвентарь и профиль обновлены.

### Общее

- Чужой `orderId`, токен другого канала и device-токен не дают доступа к заказу.
- Цена и состав берутся из серверного заказа после смены каталога.
- Повторная синхронизация после `Granted` не удваивает ресурсы.
- После сброса/удаления аккаунта повторный платформенный вход сохраняет исходный платёжный `userId` и восстанавливает активные покупки.
