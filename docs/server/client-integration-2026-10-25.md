## 1. Тестовая выдача: `POST /api/qa/grant`

### Зачем

Пока нет магазина и гачи, тестировщику и разработчику нужно быстро получить нужного персонажа, саммона, снаряжение или ресурсы прямо из игры. Раньше это делалось только через админку или ops-порт с админ-ключом — из клиента туда не достучаться.

### Как работает

- Ручка на публичном порту, со своим токеном игрока, без админ-ключа.
- Есть только на dev и stage (где включены читы). На prod её нет — `404`.
- Только для аккаунта с пометкой «тестовый». Обычный аккаунт получает `403`. Пометить: [админка](https://admin.lewdventure.online) → «Игрок» → найти по userId или deviceId → «Пометить как тестовый».
- Награду выдаёт тот же серверный сервис, что награды забега и админки: запись в журнал игрока с источником `qa:self` (видно в админке), защита от двойной выдачи по `requestId`. Цена не списывается.

```json
POST /api/qa/grant
{ "rewards": "summon:2:1,character:101010:1", "requestId": "…" }
```

`rewards` — тот же формат наград, что в конфигах, несколько через запятую:

| Что | Формат | Пример |
| --- | --- | --- |
| персонаж | `character:<id>:<копии>` | `character:101010:1` |
| саммон | `summon:<id>:<копии>` | `summon:2:1` |
| снаряжение | `equipment:<configId>:<штук>` | `equipment:5:1` |
| ресурс | `resource:<ключ>:<кол-во>` | `resource:soft_money:1000` |
| бонус аккаунта | `bonus:<id>:<кол-во>` | `bonus:1:1` |

id — из листов `Characters`, `Summons`, `Equipment` снапшота конфигов. Первая копия персонажа или саммона открывает его (в профиле `copies` = 0, это нормально), следующие копятся как при обычном получении.

Ответ — профиль целиком, как у `GET /api/player/profile`.

| Код | Когда | Что делать |
| --- | --- | --- |
| `200` | выдано, или повтор с тем же `requestId` | применить профиль из ответа |
| `400 {errors: [...]}` | неверный формат, id нет в конфигах («Rewards changed nothing in the profile.») | показать текст ошибки |
| `401` | токен | как у всех ручек |
| `403` | аккаунт не тестовый | пометить аккаунт в админке |
| `404` | prod или старая сборка сервера | ручки здесь нет |
| `409` | профиль меняется параллельно | перечитать профиль и повторить с тем же `requestId` |

### Где встроить в клиенте

Ручка ведёт себя как остальные ручки профиля, поэтому проще всего добавить её в `ProfileApi`: там уже есть отправка, применение профиля из ответа, повтор на `409` и busy-оверлей.

1. `Assets/Scripts/Core/Servers/Models/ApiRoutes.cs`: `public const string QaGrant = Api + "/qa/grant";`
2. DTO запроса в `Assets/Scripts/Game/Servers/` по образцу `PlayerCharacterRequest`: поля `Rewards` и `RequestId`.
3. `ProfileApi`: метод под `#if CHEATS` по образцу `PromoteCharacter`:

```csharp
#if CHEATS
public IObservable<Unit> QaGrant(string rewards)
{
    var requestId = _requestIdFactory.Create();
    var request = new QaGrantRequest(rewards, requestId);

    return Cover(Send(ApiRoutes.QaGrant, request, "qa grant", rewards, requestId, 0, -1));
}
#endif
```

4. Кнопки в UI читов (`Assets/Scripts/Cheats/`), рядом со сбросом прогресса в `IAccountCheatService`. Кнопка «получить юнита» собирает строку, например `$"summon:{id}:1"`, и зовёт `QaGrant`. После ответа `IProfileData` уже обновлён: экраны коллекции и сетапа увидят нового юнита без перезахода.
5. Запросы на `/api/player/claim` убрать.

Когда появится магазин, покупка будет отдельной ручкой с ценой из конфига; `qa/grant` останется только для тестов.

### Проверка

1. Аккаунт без пометки → кнопка → `403`.
2. Пометить аккаунт в админке → кнопка `summon:2:1` → `200`, саммон 2 есть в профиле и в коллекции.
3. Тот же `requestId` ещё раз → `200`, копии не выросли.
4. В админке «Игрок» → журнал: запись `grant` с источником `qa:self`.

## 2. Отказ refresh-токена: одно обновление сессии на все запросы

### Что видно на сервере

В админке «Ошибки» на dev: `[Auth] refresh token rejected userId = usr_e531…` — 19 и 20 октября. С этой выкладки сервер пишет причину: `reason = reused` — клиент прислал уже обменянный refresh-токен, `reason = unknown` — такого токена у аккаунта не было.

### Причина в клиенте

Refresh-токен одноразовый: каждое обновление выдаёт новый и гасит старый. В `Assets/Scripts/Core/Servers/Services/Client.cs` каждый запрос, получивший `401`, сам зовёт `_authService.Refresh()` (`RefreshAndRepeat`), общего обновления нет. Когда access-токен истекает (через 60 минут), а в полёте два запроса — например, профиль и характеристики, — оба шлют refresh с одним и тем же токеном. Первый проходит, второй получает `401` (`reused`). Дальше клиент входит заново по устройству (`OnRefreshUnauthorized`), так что игрок ничего не замечает, но:

- вход по устройству гасит refresh-токен, который только что сохранил первый запрос, — цепочка может повториться на следующих запросах;
- лишние запросы на сервер и предупреждения в разделе «Ошибки».

Второй источник того же отказа — две копии игры на одном устройстве (Editor и сборка) со своими `auth-session.json`: вход одной гасит токен другой. Это нормально и чинить не нужно.

### Что сделать

Держать одно обновление в полёте на все запросы: если refresh уже идёт, следующие запросы с `401` ждут его результат, а не шлют свой. На UniRx — кэш наблюдаемого обновления в `AuthService`:

```csharp
private IObservable<Unit> _refreshInFlight;

public IObservable<Unit> Refresh()
{
    if (_refreshInFlight != null)
        return _refreshInFlight;

    _refreshInFlight = RefreshOnce()
        .Finally(() => _refreshInFlight = null)
        .PublishLast()
        .RefCount();

    return _refreshInFlight;
}
```

`RefreshOnce` — нынешнее тело `Refresh()`. То же стоит сделать для `LoginDevice()`. Новый refresh-токен сохранять сразу после ответа — `Store` в `AuthService` так уже делает.

Справочник — [Client API → `POST /api/auth/refresh`](client-api.md); причины отказа в логах сервера — [QA-инструменты → Ошибки сервера](qa-tools.md).

### Проверка

На dev: войти, испортить access-токен в `auth-session.json` (refresh-токен не трогать), открыть экран, который шлёт несколько запросов сразу. В логе клиента `[Auth]` — один `Refresh`, без `Refresh 401, device`. В админке «Ошибки» по userId — без `refresh token rejected`.

## 3. Пустой слот саммона в `loadout`

`POST /api/player/loadout`: пустой слот саммона — `0`, например `"summons": [0, 1, 0]`. Отрицательный id — `400`. Раньше `0` отклонялся, теперь принимается и хранится как есть. Справочник — [Client API → `POST /api/player/loadout`](client-api.md).

Клиенту менять ничего не нужно, если пустой слот уже шлётся как `0`. Если клиент обходил это, убирая нули из списка, обход можно снять.

## 4. Без действий со стороны клиента

- Админка: лимит запросов теперь на каждый логин, 600 в минуту вместо 30 на всю панель. «Too many requests», «аккаунт не найден» и «полотно» ошибок после выдачи больше не должны появляться. Подробно — [Веб-админка](../runbooks/admin-panel.md).
- `GET /admin/qa/status` отдаёт `version` — сборку сервера. Админка по нему показывает плашку, если сама собрана из другого коммита.
- Ядро: лог «Status max stacks reached» стал Information вместо Warning. Пересобирать DLL ради этого не нужно.
- Раздел «Ошибки» в админке больше не засоряется стартовыми предупреждениями сервера; что там считается нормой — [QA-инструменты → Ошибки сервера](qa-tools.md).
